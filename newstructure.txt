## Proposed Architecture

The core idea: **each responsibility gets its own file**. Right now `DashboardController` is a god class and `FirebaseService` mixes auth, database, file encoding, and listeners. We split by *what the code does*.

### Key Splits Explained

| Before | After | Why |
|---|---|---|
| `FirebaseService.java` (1 giant file) | 4 service files | Each handles one domain — auth, chat, groups, friends |
| `DashboardController.java` (god class) | 1 coordinator + 4 sub-controllers | Each controller handles what's visible in its panel |
| `AudioRecorder.java` in controllers/ | Moved to `audio/` | It's not a controller, it's a device wrapper |
| Encoding/decoding methods scattered | `FileEncoder.java`, `ImageUtil.java` in `util/` | Pure utility — no JavaFX, no Firebase, easily testable |

---

### What `DashboardController` becomes

After refactoring it only does **3 things**:
1. `@FXML` field injection (wiring UI elements)
2. `initialize()` — calls sub-controllers to set up their panels
3. Tab switching logic

Everything else is delegated. An evaluator asking *"where does message rendering happen?"* gets a clean answer: `MessageRenderer.java`.

---

### Interfaces — where do they go?

The 5 listener interfaces (`MessageListener`, `GroupMessageListener`, etc.) move to a dedicated `listeners/` package under `services/` so they're clearly the contract between services and controllers.
